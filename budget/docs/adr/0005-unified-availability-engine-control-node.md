# Unified budget availability engine, evaluated at the control node

There were two divergent availability engines: `budget.controller` (per-combination, O(N) Python matching, exact account, floored at 0) and `budget.dashboard` (set-based `read_group` + `parent_path` rollup, not floored). We are **unifying on a single set-based engine** as the one source of truth for "available budget"; `budget.controller`'s `get_available_budget`/`check_budget_availability` become thin wrappers over it (or callers — `budget_commitment_mixin`, `budget_transfer`, `budget_transfer_line` — migrate). One definition of "available" feeds the reservation check, status reports, and KPI sums alike.

**Availability is evaluated at the _control node_.** For a reservation against budgetable account `X`, the control node is the nearest budgetable ancestor-or-self of `X` that carries posted appropriation. `available(X) = Current Budget − Used`, both **rolled up over the control node's subtree** — so two sibling reservations under a shared funded ancestor cannot each spend the parent's money. Direction is one-way: appropriation may sit **at or above** the reservation node, **never below** it.

**Budget is controlled per `(budget.account × dimension combination)`, not per account alone.** The check takes the reservation's `analytic_distribution` (JSON) — *not* a fixed set of dimension fields — so the engine is dimension-agnostic and needs no code change when an analytic dimension is added or removed. The accounting dimensions are six (`departments`, `sources`, `funds`, `activities`, `kmitl_project`, `procurement_plan`), of which **five are used at once** because `kmitl_project` and `procurement_plan` are mutually exclusive on a given line.

**The same control-node model applies to every axis, derived generically from `account.analytic.account.parent_path` — not from the plan.** All analytic *plans* are flat; the hierarchy lives on the analytic *accounts*. So per dimension value: if the analytic account has ancestors, appropriation at an ancestor covers the reservation (one-way, Case A); if it is flat/root (e.g. `sources`), it matches exactly. The same `parent_path` rule that resolves the `budget.account` control node resolves each dimension's — no dimension is special-cased by name.

**Matching is set-based on stored columns, so every controlled dimension needs a column.** The budget line models historically carried columns for only four dimensions (department/source/fund/activity); `kmitl_project` and `procurement_plan` lived only inside the `analytic_distribution` JSON, which Odoo 16 cannot `read_group`/`child_of` efficiently. Decision **G1**: add stored convenience columns `kmitl_project_analytic_id` and `procurement_plan_analytic_id` (computed from `analytic_distribution`, like the existing four) to the budget line/header models and extend each model's `_analytic_keys` registry. The public API still takes `analytic_distribution`; internally the engine maps known plan codes → columns. Adding a future controlled dimension = add a column + one registry entry (localised), not a JSON-matching rewrite (rejected: slow/unsupported) nor a normalized analytic-line model (rejected: too large for now).

**Data dependency:** the new columns backfill from each line's existing `analytic_distribution`. Appropriation that was posted *without* a `kmitl_project`/`procurement_plan` tag will not match a reservation that carries one (match → 0 → blocked); aligning that is a **deployment-time data backfill / appropriation-process** concern, not an engine-design one.

## Considered options

- **Coexist** (keep `budget.controller` for single checks, extract a separate shared primitive) — rejected: two definitions of "available" drift apart; a picker that *shows* dashboard numbers but *enforces* controller numbers would mislead the user; and the O(N) loop is exactly the performance problem we set out to remove.
- **Account axis — exact/deepest-wins (P1) vs sum-up-chain (P2):** chose **P2** (sum funded levels up the chain). Coarse budgets — งบบุคลากร (personnel), งบโครงการ (project) — are appropriated at an upper node with empty leaves, and reservations at those leaves must reach the upper pool. P1 would strand them at ฿0.

## Consequences

- **Case A — one funded level per chain — is the assumption for the first implementation.** If a chain is funded in detail at the leaves it is *not* also funded at the category, and vice-versa. The control node is then unique per chain, so the dashboard's rolled-up Current/Used **at that node** *is* the availability — reuse it directly; the only new step is resolving the control node (walk up to the nearest funded budgetable node).
- **Case B — multiple funded levels on one chain** (e.g. funded at `51000` *and* at leaf `51010` simultaneously) — requires deepest-first draw-down attribution (each reservation attributed to exactly one pool, cascading up only when the deeper pool is exhausted) to stay double-count-safe. **Noted as future work; not implemented now.**
- Appropriation entered at a level that does not align with where reservations occur reads as ฿0 available at the leaf. Appropriation must land on (or above, per Case A) the control node.
- **One figure, not floored.** `used = Σ reserve lines` over active commitments (`reserved`/`partial`/`done`); `available = Current Budget − used`, allowed to go **negative** so over-commit is visible and report/widget show the identical number. The controller's `max(0, Σreserve − Σconsume)` net-reserve variant is retired; obligate/consume stay a waterfall *under* reserve (ADR 0001). Blocking an over-commit is a separate policy layer (`budget.allow_negative`), not a flooring of the figure.
- **One engine, three entry points over shared primitives:** (1) a single-combination **availability check** for reservation — the only path that resolves a control node per axis, but it runs on *one* combination so it is cheap; (2) a **hierarchical report grid** — `budget.account`-axis rollup with dimensions as filters (today's dashboard); (3) **KPI sums by arbitrary domain**. Only (1) needs control-node resolution; (2) and (3) use plain rollup/`read_group`.
