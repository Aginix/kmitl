# Record payment type per actual-allocation row; route billing by type; defer advance clearing

> **Note (2026-07):** the §"Scope 2 sketch" below is **superseded by [ADR-0003](0003-per-participant-borrowing-against-an-approved-request.md)** — borrowing turned out to be per *participant* (not per recipient-matched row), the Funding Loan on an `advance` row is **chosen** rather than auto-matched by partner, and the loan clears itself instead of being written to from billing. The per-row `payment_type` decision and the billing routing recorded here still stand.

Each **actual expense allocation** row (`approval.request.allocation`) now carries a **payment type** — `direct` (จ่ายตรง — the institute pays the named recipient directly), `prepaid` (สำรองจ่าย — a participant fronts the cost themselves, then claims it back), or `advance` (เงินยืม — the recipient drew a สัญญายืม and the expense clears that loan). The type is recorded **per row, at the `actual` stage** (after the mission), because one recipient may mix สำรองจ่าย and ยืมเงิน across their own expenses. Billing routes by type: `direct` and `prepaid` rows become disbursement lines; `advance` rows are excluded from the disbursement (the money already left as a loan) and clear against the borrower's สัญญายืม instead.

This **amends [ADR-0001](0001-plan-vs-actual-payee-off-the-plan.md) §D6**, which removed `payment_type` from the form because advance-vs-direct is unknown at approval. That reasoning holds for the *plan*; the type is both knowable and needed at the *actual* stage. So `payment_type` returns — relocated from the plan header to the actual-allocation row.

## Considered options

- **Payment type per recipient (group-level).** Rejected: UAT confirmed one recipient may front some expenses (`prepaid`) and borrow for others (`advance`), so the type must be per row, not per person.
- **Informational tag only, billing unchanged.** Rejected: an `advance` row that still became a disbursement line would double-pay (the loan already disbursed that money). Routing must react to the type.
- **Build per-recipient advance clearing now (scope 2).** Deferred: fanning the single `advance_payment_id` out to one สัญญายืม per recipient, writing `usage_line` clearing, and reconciling over/under-return is exactly the in-flight `advance_payment` overhaul's territory (per-line payment_type, BR-clearing, ทยอยยืม). Doing it here would collide. This ADR ships the **seam**; the overhaul supplies the engine.

## Consequences

- **`approval.request.allocation.payment_type`** — Selection `direct` / `prepaid` / `advance`, per row, **required**, default `prepaid` (the common travel case), editable in `actual`.
- **Billing → one DR (interim).** `disbursement.request` does not yet support multiple payment types on one document (its header `payment_type` is single-valued and there is no per-line type). So scope 1 emits **exactly one multi-partner DR with header `payment_type = direct`**, carrying every `direct` and `prepaid` row; `advance` rows are excluded. The direct/prepaid distinction is preserved on the allocation rows (and the งบหน้าฯ voucher) but is **not** reflected on the DR header yet. An AR whose rows are *all* `advance` yields **no DR** and bills on clearing alone.
- **Target state (blocked on the DR module):** once `disbursement.request` gains per-line payment type, the AR passes each row's `payment_type` onto its DR line and the header rule is revised — **no AR data-model change needed** (the allocation already stores the type). Adjusted on the AR side when the DR side lands.
- **Anti-double-pay.** `advance` rows never enter a disbursement; billing an `advance` row through the DR path is blocked. (Independent of the one-DR collapse above — it concerns *whether* a row is disbursed, not *which* DR header it lands under.)
- **Seam for scope 2:** a nullable `approval.request.allocation.advance_payment_id` links an `advance` row to the borrower's สัญญายืม (used by the งบหน้าฯ voucher and later consumed by the overhaul's clearing). No per-recipient advance creation or `usage_line` writing happens in this scope.
- **Interim meaning of `billed`:** `direct`/`prepaid` rows are disbursed; `advance` rows are recorded and marked *รอเคลียร์* (pending clearing) — the สัญญายืม is not cleared until the overhaul wires the clearing step. Surfaced in the UI so `billed` is not mistaken for "loans settled."
- **Reporting:** the disbursement voucher (งบหน้าใบสำคัญคู่จ่าย) and the approval-request PDF both render a **ประเภทการจ่าย** column per row, so `advance` rows are visible on the face of the document. Totals stay the **full actual-expense** figure (advance is listed, not netted out) — chosen over excluding advance from the voucher total, so the cover sheet still enumerates every ใบสำคัญ.
- **Scope 2 sketch (for when the overhaul lands):** (1) `advance_payment_ids` O2m on the request, one สัญญายืม per borrowing recipient, matched by `requested_by_partner_id` = `allocation.partner_id`; (2) at billing, each `advance` row writes a `usage_line` `{agreement_id, amount, date, note, evidence}` on its linked สัญญายืม (usage carries amount only — itemisation stays on the AR); (3) actual < loan → `return_line` for the remainder; actual > loan → the excess becomes a `direct`/`prepaid` DR row (over-return-split, capped by `advance.payment.usage.line._check_total_not_exceeding`).
- **Entry UX (this feedback round):** the grouped allocation widget gains a per-recipient **"เพิ่มรายการ"** action that adds a row with the recipient pre-filled (the name is not re-entered); `payment_type` remains a per-row choice.
- **Pre-production (UAT):** applied in place — no data migration, no manifest version bump.
